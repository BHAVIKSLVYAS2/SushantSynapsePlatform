## Reviewable changes

- Chambers clients, matters, hearings, tasks, fees and payments use D1. Existing roles, app access, account IDs and preferences remain. Payment checks and hearing outcome + next date remain atomic.
- Login retains existing email/password credentials and scrypt hashes. Signed-in users receive a secure HttpOnly session cookie; current active account, role and app access are loaded from D1 on each request. Login is rate-limited to six attempts per minute per connecting IP. Email requires valid unique format but no ownership verification, OTP or Cloudflare allow-list. Access mode remains optional code and is not enabled in this deployment.
- Private Chambers documents, Samaj photos and Samaj message attachments are stored in D1 BLOBs, limited to 1,000,000 bytes each and 100,000,000 bytes total. SQL triggers enforce aggregate capacity inside the same transaction as file metadata, record and audit writes. Downloads verify byte length and SHA-256 and require current app access. Existing larger files remain in the full local recovery bundle and original databases; the import report lists omissions. Eligible Samaj files are supported by the import/recovery tools.
- `FULL_APPS=true` enables DIGITAL SAMAJ, BatchFee and Tournament workspaces, private Fund workflows, saved News generation and the ritual calendar API. Existing records remain in the same production D1 database. Large interactive backup/restore is still disabled; owners use verified offline D1 export/recovery. Public static tools, Fund comparison/source handlers and temporary News remain available. Arena requires its own secret before shared votes work.
- The initial workspace limit is 250 Chambers records, 256 KiB of aggregate record JSON, 8 KiB per record, and 25 accounts. SQL triggers enforce capacity inside every atomic write, including a new hearing. These are deliberately conservative application limits, distinct from Cloudflare's account quotas.
- Each full-app private request may issue at most 49 D1 statements (45 in reduced mode), below the Free limit of 50. An oversized batch fails before execution. The configured maintenance switch stops APIs. Workers Free's 10 ms CPU cap may still reject some operations: local emulation does not prove production CPU suitability.

## Deployment and recovery procedure

1. Owner confirms **Workers Free** in the dashboard (confirmed 2026-10-11). Current OAuth credentials authenticate successfully but cannot read subscriptions; Standard usage-model metadata is not proof of Free billing. R2 is not enabled. Do not upgrade or cancel other account services automatically.
2. Select a separate staging hostname first; do not replace the production route before acceptance. The user's latest commit/deploy instruction authorizes this work. Staging workers.dev access is currently disabled; enable it explicitly only during future staging acceptance and close it afterwards.
3. Keep `AUTH_METHOD=password` and the `AUTH_LIMITER` binding. Preserve source hashes and account IDs during import. Setup is protected by a secret and cannot run when source accounts exist; no new password or verified email is required for migrated accounts.
4. Create a **new** staging D1 database, set its UUID and exact HTTPS `PUBLIC_ORIGIN`, then apply `d1-free-migrations`. There are no R2 bindings. Use the free configuration, not `wrangler.fullstack.jsonc`.
5. Export the authoritative SQL Server source using the existing full backup command. Run `node infrastructure/cloudflare/free-import.cjs --bundle <full-bundle> --output <new-directory>`. This validates the full backup and produces D1-only SQL plus an omission report without changing source data. It imports eligible Chambers document bytes, using statements below D1's 100 KB SQL limit. It refuses excess record/account/aggregate document capacity rather than truncating records. Keep the full bundle securely for omitted original files and disabled apps.
6. Import the generated SQL only into that fresh, unbound staging database. Verify row checksums/counts, account IDs, record insertion order, preferences and foreign keys before deploying. The initial production import was remotely verified at cutover; future imports still require independent remote verification.
7. Deploy the free staging Worker and verify real password login, mobile Chambers, role revocation, payment concurrency, hearing rollback and CPU use. If valid operations exceed Free CPU allowances, reduce work further instead of enabling Paid. Preserve the production Arena secret with `--keep-vars`; never print or commit it. Staging fixtures must not enter the fresh production target.
8. After acceptance, freeze old writes, take a fresh verified export, import a new production D1 target and switch the reviewed route. Retain the old database/recovery bundles. New cloud writes must be reconciled before rolling back to the old database.

## D1 document recovery

Freeze writes with maintenance mode, then export the remote D1 database using `wrangler d1 export <database> --remote --output <private-snapshot.sql>`. Run `npm.cmd run db:cloudflare:free-recovery -- --sql <private-snapshot.sql> --output <new-private-directory>`. This offline tool validates foreign keys, table checksums and exact document hashes, excludes sessions, and generates a verified restore with chunked SQL statements. Restore only into a new unbound D1 database with all free migrations applied; verify its remote export before switching bindings. Recovery files include account hashes and private records and must never be committed or published. Local verification does not establish successful remote recovery.

Local commands: `npm.cmd run build:cloudflare:free`, `npm.cmd run db:d1:free:local`, `npm.cmd run dev:cloudflare:free`, `npm.cmd run test:cloudflare`. The initial free schema is a copy of the shared initial migration; future changes need new numbered migrations in both targets where applicable. Never regenerate an applied migration.
